# 서버 구조 및 핵심 기능 정의

기준일: **2026-11-22** · 백엔드 **v1.5.0** · 중간발표 범위 **B01~B05 설계·Mock**

이 문서는 현재 실행 코드와 SQLite 스키마를 설명한다. 실제 센서·AI 대신 모의 입력으로 검증한 부분과 다른 파트와 연결해야 하는 부분을 구분한다. 전체 시험 결과는 [TEST_REPORT.md](TEST_REPORT.md), 요청·응답 계약은 [API_SPEC.md](API_SPEC.md)에서 확인한다.

## 1. 개발 목표와 담당 경계

어르신의 위험 판단 결과·생활 패턴을 기록하고, 보호자·어르신·관리자가 필요한 정보를 권한에 맞게 확인하도록 한다. 복약 일정과 안내 기록을 관리하며 앱·웹에 REST 조회와 WebSocket 실시간 전달을 제공한다.

| 파트 | 담당 내용 | 백엔드와 주고받을 내용 |
|---|---|---|
| 하드웨어·게이트웨이 | 센서 측정·장치 통신·현장 스피커 출력 | 장치·대상 ID, 이벤트 시각, 하트비트, 활동 이벤트, 음성 명령 조회·ACK |
| AI | 센서·영상 분석, 낙상·활동·생활 패턴 판단 | 위험 단계·근거 요약, 관찰 기간·통계, 1차 의심과 카메라 결과 |
| 백엔드 | 입력·권한·중복 검증, SQLite 기록, 조회·일정·명령·알림 관리 | 검증된 요청 수신, 저장 결과, REST 응답, 실시간 이벤트, 가상 푸시 기록 |
| 프론트 | 앱·웹 화면과 입력, 서버 응답·알림 표시, 전화 앱 연결 | 로그인·조회·일정 변경 요청, 빈 목록·연결 끊김·오류 표시, 상세 화면 이동 |

백엔드는 AI 모델 추론이나 센서 보정을 수행하지 않는다. 119·어르신 전화 버튼은 프론트에서 기기의 전화 기능을 여는 동작이며, 서버가 전화나 신고를 수행하는 기능은 없다. 어르신 전화번호는 목록 응답에 본인 계정의 번호 또는 `null`로 제공한다.

## 2. 서버 구조와 사용 기술

연동 예정 흐름은 ‘센서 → 게이트웨이·AI → 백엔드 검증·저장 → 앱·웹 조회·실시간 표시’다. 현재는 시연 화면·HTTP 요청이 실제 센서와 AI의 입력을 대신한다. [서버 구성도](architecture.svg)에 같은 경계를 표시한다.

| 구성 | 현재 사용 기술·역할 |
|---|---|
| 언어·웹 서버 | Python, FastAPI, Uvicorn 단일 프로세스·워커 1개 |
| 입력·응답 검증 | Pydantic 모델, 알 수 없는 필드 금지, 시각·범위·필수값 검증 |
| 저장 | 표준 `sqlite3`, SQLite WAL·외래키 검사·busy_timeout 5초 |
| 조회·수신 | HTTP JSON REST, `/api/v1` 버전 경로 |
| 실시간 전달 | 대상별 `/ws/live`, 관리자 전체 `/ws/admin/live`, DB 커서 재조회 |
| 로그인 | PBKDF2-HMAC-SHA256 비밀번호 해시, DB에 저장하는 만료·철회 가능한 Bearer 세션 |
| 개발 확인 | Swagger, 가상 계정·입력·푸시 기록, 브라우저 확인 화면, 자동 시험 |

SQLAlchemy와 JWT는 현재 사용하지 않는다. 사용자 세션은 임의 토큰을 발급하고 DB에는 토큰의 SHA-256 해시를 저장한다. Mock 로그인은 별도의 고정 테스트 토큰 방식이다. [로그인 설명](LOGIN_GUIDE.md)을 함께 참고한다.

| 파일·폴더 | 현재 역할 |
|---|---|
| `app/main.py` | REST·WebSocket, 권한, 이벤트 처리, 복약·연결 점검, 화면 경로 |
| `app/models.py` | 요청·응답 모델과 OpenAPI 자료형 |
| `app/auth.py` | 비밀번호 검사, 세션 발급·만료·로그아웃, 로그인 실패 제한 |
| `app/fall_assessments.py` | 단계별 카메라 결과 연결·중복·순서 제어 |
| `app/db.py` | 연결·트랜잭션·가상 초기 데이터·DB 버전 적용 |
| `app/schema.sql` | 테이블·PK·FK·UNIQUE·CHECK·인덱스 |
| `static/` | API를 직접 호출하는 개발용 연동·관리자·로그인 확인 화면 |
| `tools/export_contract.py` | 코드·SQL에서 명세·예시·자료형·데이터 사전 생성 |
| `tests/` | 임시 DB를 이용하는 기능·권한·오류·중복·복구 시험 |

DB 기본 위치는 `data/mock.sqlite3`이며 `DATABASE_PATH`로 지정할 수 있다. 요청 처리에서 원본 이벤트·사고·현재 상태·알림·전달 이벤트를 트랜잭션으로 기록한다. WebSocket은 커밋된 `event_feed`를 읽는다. 서버를 재시작해도 DB에 저장한 일정·사고·만료 전 세션은 유지한다. 다중 서버·고빈도 원시 센서 스트림·상용 운영 성능 검증은 아직 하지 않았다.

## 3. 사용자별 기능과 권한

| 사용자 | 조회 대상 | 주요 기능 |
|---|---|---|
| 보호자 `GUARDIAN` | `senior_guardians`에 연결된 어르신 | 상태·장치·사고·패턴 확인, 복약 일정 CRUD, 낙상·패턴 알림 기록 |
| 어르신 `SENIOR` | `seniors.user_id`로 연결된 본인 | 본인 상태·일정 확인, 본인 일정 등록·수정·삭제, 복약 알림 |
| 관리자 `ADMIN` | 전체 대상 | 전체 상태·사고 목록·장치 확인, 전체 경고 채널, 개발용 모의 입력 |
| 장치 인증 | 인증된 게이트웨이와 직속 장치 | HTTP 이벤트 수신, 음성 명령 조회와 결과 ACK |

대상별 API는 서버가 연결을 다시 검사한다. 화면의 역할 선택만으로 권한이 생기지 않는다. 현재 코드에서 관리자는 대상별 복약 관리 API도 허용되지만 관리자 프론트의 업무 범위는 조회 중심으로 협의한 상태다. API 권한과 화면 제공 범위는 구분한다.

초기 가상 데이터는 관리자·보호자·어르신 계정 3개, 어르신 4명이다. 보호자는 연결된 3명, 어르신은 본인 1명, 관리자는 전체 4명을 조회한다. 현재 게이트웨이 테스트 토큰은 첫 가상 대상의 게이트웨이와 직속 장치만 허용한다. 실제 장치별 자격 증명 발급·교체는 후속 과제다.

## 4. SQLite DB 설계

현재 스키마는 **21개 테이블·141개 컬럼, `user_version=4`**다. 실제 정의는 [app/schema.sql](../app/schema.sql), 전체 필드는 [DATA_DICTIONARY.md](DATA_DICTIONARY.md), 관계는 [요약 ERD](erd.svg)·[전체 관계 ERD](erd-relationships.svg)와 [필드 포함 ERD](erd-detailed.svg)에서 확인한다.

| 그룹 | 테이블 | 저장 목적과 주요 제약 |
|---|---|---|
| 사용자·대상 | `users`, `seniors`, `senior_guardians` | 계정, 본인 0~1 연결, 보호자↔어르신 N:M 복합 PK, 현재 위험 상태 |
| 장치·연결 | `devices`, `device_logs` | 대상별 장치, 게이트웨이 부모 연결, ONLINE/OFFLINE 전환과 원인 |
| 수신·사고 | `ingested_events`, `sensor_logs`, `incidents`, `incident_details` | 전역 고유 이벤트, 센서 근거 요약, 사고 목록·상세 |
| 단계별 판단 | `incident_assessment_events` | 같은 사고의 1차·최종·실패·중복 수신 연결, 반영 여부 |
| 복약 | `voice_assets`, `medication_schedules`, `medication_logs`, `speaker_commands` | 음성 정의, 반복 일정, 일정·날짜별 안내 이력, 명령·ACK |
| 생활 패턴 | `lifestyle_patterns` | 관찰 구간·통계·단위·이상 여부 |
| 알림·복구 | `push_tokens`, `notifications`, `event_feed`, `idempotency_keys` | 설치별 토큰, 사용자별 가상 알림, 전역 커서, 등록 재시도 응답 |
| 비밀번호 인증 | `auth_sessions`, `auth_login_attempts` | 해시 처리한 세션 토큰·만료·철회, 계정·접속 단위 실패 제한 |

저장 형식과 관계를 다음처럼 적용한다.

- 대상·사용자·장치·사고·이벤트 ID는 UUID 문자열을 TEXT로 저장한다. 커서·단계별 수신 순번은 INTEGER, 센서 요약은 REAL 또는 INTEGER다. 음성 ID `TYPE_A/TYPE_B` 등은 UUID가 아닌 명시된 문자열이다.
- 일반 시각은 UTC ISO 8601 TEXT, 생년월일은 `YYYY-MM-DD`, 복약 시각은 KST 기준 `HH:mm`, 반복 요일은 검증된 JSON TEXT다. boolean은 SQLite에서 INTEGER 0/1이다.
- 값이 없으면 SQL NULL을 사용한다. 미등록 전화번호·센서값·판단 근거를 0이나 문자열 `"NULL"`로 대신하지 않는다.
- `seniors.status_event_id`는 최신 판단 이벤트를 참조한다. 초기에는 NULL이며 이벤트 저장 후 연결한다. 이 관계와 `devices.parent_device_id` 자기 참조는 의도한 관계다.
- 센서 로그는 이벤트별 충격·높이·신뢰도 요약이다. 원시 압전 파형·ToF 프레임·카메라 영상 전체를 저장하는 구조는 아니다.
- 일정 삭제는 `deleted_at`을 기록하는 소프트 삭제다. 사고·안내·수신 이력은 가상 데이터 초기화를 제외하고 보존한다. 실제 개인정보·영상 보관·삭제 기간은 팀 합의가 필요하다.

## 5. 핵심 처리 흐름

### 위험 판단과 초기 상태

장치·대상 검사 → 입력 검증 → `event_id` 중복 검사 → 원본·센서 요약 저장 → CAUTION/DANGER 사고 생성 → 최신 발생 시각인 경우 현재 상태 갱신 → 전달 이벤트·가상 알림 기록 순서다. 같은 이벤트 ID와 같은 본문은 중복 처리하고, 다른 본문이면 409로 거절한다. 오래된 이벤트는 최신 위험 상태를 덮어쓰지 않는다.

초기 `status_event_id=null`은 **판단 기록 없음**이다. 초기 기본값 `NORMAL`과 DB 초기 시각을 실제 AI 판단과 판단 시각으로 표시하지 않는다. 관리자 확인 화면은 ‘판단 기록 없음’과 시각 `—`를 표시한다. 자세한 응답·표시 규칙은 [INITIAL_STATUS.md](INITIAL_STATUS.md)를 따른다.

일회성 위험 수신에서 미취소 DANGER는 연결 보호자에게 `FALL_ALERT` 기록을 만든다. `gesture_cancelled=true`는 사고를 `CANCELLED`로 남기고 현재 유효 상태를 NORMAL로 처리한다. 원본 위험 단계는 별도 기록으로 남는다.

### 카메라 단계별 재검증

현재 구현은 팀 협의용 **제안 규격**이다. 실제 카메라를 켜거나 AI를 호출하지 않는다. 송신 측이 만든 같은 `incident_id`에 새 전송별 `event_id`를 보내는 구조다.

| 입력 | 사고·현재 상태 처리 |
|---|---|
| `PRELIMINARY / PENDING_VERIFICATION` | CAUTION·OPEN 생성, 이 사건이 최신이면 현재 주의 |
| `FINAL / COMPLETED / confirmed_fall=true` | 같은 사고를 DANGER·OPEN, 현재 상태 근거가 이 사건이면 위험 |
| `FINAL / COMPLETED / confirmed_fall=false` | 같은 사고를 CANCELLED, 현재 상태 근거가 이 사건이면 정상 |
| 카메라 실패·시간 초과·데이터 부족 | 실패 이유 기록, 의심·현재 상태 유지, 이후 최종 재시도 가능 |

초기 의심 없이 최종이 먼저 오면 409다. 같은 요청은 사고·알림을 반복하지 않는다. 이미 확정한 결과를 다른 내용으로 덮어쓸 수 없고, 이전 사건의 늦은 결과는 더 새로운 현재 상태를 바꾸지 않는다. 카메라 `false`나 AI `UNKNOWN`을 임의로 ‘최종 오탐 취소’로 변환하면 안 된다. AI 실제 위험 단계와 융합 결과 의미를 합의해야 한다. [CAMERA_REVIEW.md](CAMERA_REVIEW.md)에 필드와 재시도 규칙이 있다.

### 복약 일정과 안내

보호자는 연결 대상, 어르신은 본인 일정을 CRUD한다. 앱 복약 안내는 활성 일정의 KST 시간 구간에 활동 감지 없이 생성한다. 스피커 명령은 같은 구간에서 최근 활동이 감지될 때 생성한다. 두 안내는 별개이며 같은 일정·현지 날짜 중복을 차단한다. 게이트웨이가 명령을 조회하고 ACK해야 안내 성공으로 기록한다. 성공 ACK는 실제 복약 완료를 뜻하지 않는다. [SENIOR_MEDICATION.md](SENIOR_MEDICATION.md)에 상세 규칙이 있다.

### 장치 연결과 복구

ONLINE 장치에 90초 넘게 하트비트가 없으면 OFFLINE과 원인을 기록한다. 장치 하나라도 끊기거나 등록 장치가 없으면 `data_freshness=STALE`이다. 이는 장치 연결 요약이며 AI 판정의 유효 기간이 아니다. 마지막 위험 상태는 연결이 끊겨도 보존한다.

대상별 채널과 관리자 전체 채널은 DB의 증가 커서로 누락 이벤트를 다시 읽는다. 클라이언트는 처리한 커서를 저장하고 최신 REST 상태·목록을 다시 읽는다. 두 채널은 허용 이벤트·커서 범위·오류 처리 규칙이 다르므로 [API_SPEC.md](API_SPEC.md)의 표를 적용한다.

후속 B06~B14 관련 HTTP 수신·복약 엔진·조회·카메라·실시간·연결·오류 기능은 모의 입력으로 선행 구현했다. 해당 WBS를 실데이터까지 완료했다고 표시하지 않는다. B15 응답시간·안정성, B16 전체 통합, B17 최종 배포·시연 문서화의 완료도 이번 기능 시험으로 대신할 수 없다.
