# 관리자 전체 어르신 현황 조회

2026년 11월 17일 · API v1.3.0 · 기존 관리자 규격 초안을 기준으로 백엔드 구현

## 이번에 완료한 것

관리자가 전체 어르신의 이름, 마지막 위험 상태, 상태 갱신 시각, 장치 연결 수를 한 번에 조회할 수 있다.
기존 대상별 상태 조회와 같은 상태·연결 기준을 사용한다. 목록은 이름순이며 이름이 같으면 senior_id 순으로 정렬한다.
장치가 끊겨도 마지막 위험 단계와 갱신 시각은 유지한다. 장치가 하나도 없는 경우 연결 0 / 끊김 0, data_freshness=STALE로 반환한다.
로그인 화면을 추가 구현할 필요 없이 개발용 관리자 계정으로 확인할 수 있다. 실제 프론트 연결은 화면 코드가 준비되면 진행한다.

## 직접 확인하는 법

1. 서버가 켜진 터미널에서 Ctrl+C를 눌러 멈춘다.
2. safehome-backend 폴더의 터미널에서 아래 명령을 입력한다. 검은 창은 열어 둔다.

```powershell
.\.venv\Scripts\python.exe run.py
```

3. 브라우저에서 http://127.0.0.1:8000/admin-test 를 연다. 기존 첫 화면 위의 ‘관리자 전체 현황’을 눌러도 된다.
4. 가상 어르신 4명의 이름·정상/주의/위험·갱신 시각·장치 연결 수가 나오는지 본다.
5. ‘한 화면에’를 ‘2명씩’으로 바꾸고 ‘다음’을 누른다. 나머지 2명이 나온다. ‘이전’으로 돌아갈 수 있다.
6. ‘서버가 보내준 응답 보기’를 누르면 실제 응답 JSON을 펼쳐 볼 수 있다.

새로 조회는 현재 페이지를 다시 읽는다. 대상 수가 줄어 현재 페이지가 비었으면 ‘이전’으로 돌아가거나 ‘한 화면에’를 바꿔 첫 페이지부터 확인한다.
새 기능이 보이지 않으면 서버를 껐다 켠 다음 브라우저에서 Ctrl+Shift+R로 새로고침한다.
이 화면은 자동으로 개발용 관리자 로그인을 하므로 ENABLE_MOCK_AUTH=0으로 켠 서버에서는 안내 오류가 표시된다. API 자체는 유효한 관리자 비밀번호 로그인 세션으로도 이용할 수 있다.

## 프론트 연결 규격

`GET /api/v1/admin/seniors?page=1&size=20`

요청 헤더: `Authorization: Bearer <관리자 토큰>`
첫 개발 시험에는 기존 `admin-demo-token`을 쓴다. 실제 비밀번호 로그인 세션의 관리자 토큰도 사용할 수 있다. 화면에서 관리자 역할을 골랐다는 이유만으로 권한이 부여되지 않는다.

| 요청 값 | 의미 | 범위 |
|---|---|---|
| page | 페이지 번호 | 기본 1, 1 이상 |
| size | 한 번에 받을 인원 | 기본 20, 1~100 |

| 응답 항목 | 화면에서 사용할 정보 |
|---|---|
| items[].senior_id | 상세 조회할 어르신 ID |
| items[].name | 어르신 표시명 |
| items[].risk_level | NORMAL=정상, CAUTION=주의, DANGER=위험 |
| items[].last_updated_at | 마지막 위험 상태 갱신 시각. UTC 문자열을 한국 시각으로 표시 |
| items[].data_freshness | FRESH=모든 등록 장치 연결, STALE=끊긴 장치가 있거나 등록 장치 없음 |
| items[].device_summary.online | 연결된 장치 수 |
| items[].device_summary.offline | 끊긴 장치 수 |
| page, size, total, total_pages | 현재 페이지·페이지 크기·전체 인원·전체 페이지 수 |

위험 상태와 장치 연결은 서로 다른 정보다. 예를 들어 마지막 위험 상태가 DANGER이고 장치가 모두 끊겼으면 위험 표시와 끊김 표시를 함께 유지한다.
최근 90초 동안 하트비트를 보내지 않은 장치는 기존 규칙에 따라 OFFLINE으로 변경된다. 갱신 시각은 화면을 조회한 시각이 아니라 마지막 위험 상태가 갱신된 시각이다.

응답 형태:

```json
{
  "items": [
    {
      "senior_id": "00000000-0000-4000-8000-000000000101",
      "name": "김안심(가상)",
      "risk_level": "NORMAL",
      "last_updated_at": "2026-11-17T01:00:00.000000Z",
      "data_freshness": "FRESH",
      "device_summary": {"online": 5, "offline": 0}
    }
  ],
  "page": 1,
  "size": 20,
  "total": 1,
  "total_pages": 1
}
```

위 JSON은 한 명만 등록된 경우의 형태 예시다. 개발용 기본 DB는 4명이며 현재 실제 값은 확인 화면이나 docs/examples.json에서 확인한다.
등록된 사람이 없으면 items=[], total=0, total_pages=0이다. 전체 인원이 있어도 마지막 페이지를 넘기면 items=[]이며 total과 total_pages는 실제 값을 유지한다.
미인증·만료 토큰은 401, 보호자·어르신 계정은 403, page/size 범위 위반은 422다. 오류 형태는 기존 error_code, message, details, request_id, timestamp를 유지한다.
개인 전화번호·비밀번호·토큰은 이 목록에 포함하지 않는다.

frontend/api.ts의 `adminSeniors(page, size)`와 frontend/schemas.ts의 AdminSeniorPage 타입을 제공한다. Swagger의 ‘관리자’ 항목과 생성된 요청·응답 예시에도 반영했다.
새 API는 목록을 조회하는 HTTP 요청이다. 전체 사건 목록·전체 경고 실시간 수신은 이번 구현에 포함하지 않았다. 관리자 화면의 최종 요구사항은 프론트와 별도로 맞춘다.

## 확인한 내용

기존 기능을 포함한 자동 시험 45개 통과, 실패 0개. 새 관리자 조회 관련 시험은 11개다.
관리자 권한, 비관리자 차단, 기존 개별 상태 조회와 일치, 하트비트 만료 시 연결 수 반영·위험 상태 유지, 장치 없는 대상, 빈 목록, 같은 이름의 안정적 정렬, 페이지 경계와 잘못된 page/size를 확인했다.
개발용 자동 로그인이 꺼진 상태에서도 비밀번호로 로그인한 관리자는 조회할 수 있고, 로그아웃 후에는 차단됨을 확인했다.
이번 작업은 DB 테이블·개인 PC의 실제 데이터를 변경하지 않는다. 기존 조회 시의 하트비트 만료 처리 규칙은 그대로 적용된다.


실제 브라우저에서 가상 대상 4명의 전체 현황, 2명씩 표시, 다음·이전 페이지 이동, 서버 응답 펼치기를 확인했다. 별도 메모리 DB의 시험 서버로 확인했으며 사용자의 실제 DB를 수정하지 않았다.
최신 OpenAPI는 현재 코드와 일치한다. 30개 경로·32개 요청/응답 예시 중 요청 본문 11개와 응답 28개를 모델로 검증했다. 관리자 화면 JavaScript 문법 검사도 통과했다.
