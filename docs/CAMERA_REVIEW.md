# 카메라 재검증 결과 반영과 중복 이벤트 제어

> 최신 기준 안내(2026-11-22): 현재 v1.5.0은 SQLite 21개 테이블·141개 열, HTTP 34개 경로·36개 작업, 자동시험 87개 통과다. 아래의 기능 추가일·당시 시험 개수는 이력이다. 최신 [ERD](erd.svg)·[API 규격](API_SPEC.md)·[시험 기록](TEST_REPORT.md)을 함께 본다.

2026-11-18 · 백엔드 v1.5.0 · 모의 구현 및 연동 제안 규격

## 이번에 만든 것

같은 사고 ID에 1차 의심과 카메라 재검증 결과를 이어 붙인다. 카메라 결과를 새 사고로 만들지 않고 기존 사고를 갱신한다. 기존 일회성 위험 수신 API도 그대로 사용할 수 있다.

| 들어온 내용 | 사고 기록 | 현재 상태 |
|---|---|---|
| 1차 의심 | CAUTION·OPEN, 카메라 대기 | 이 사건이 최신일 때 주의 |
| 최종 낙상 확정 | 같은 사고를 DANGER·OPEN으로 갱신 | 이 사건이 현재 상태의 근거일 때 위험 |
| 최종 오탐 취소 | 같은 사고를 CANCELLED로 갱신 | 이 사건이 현재 상태의 근거일 때 정상 |
| 카메라 실패·시간 초과·데이터 부족 | 같은 사고를 의심 상태로 유지하고 실패 사유 기록 | 정상으로 바꾸지 않고 기존 상태 유지 |
| 이미 처리한 동일 요청 | 새 사고·새 상태 변경·새 알림 없음 | 유지 |
| 이전 사고의 늦은 최종 결과 | 해당 과거 사고의 기록만 갱신 | 더 새로운 사건의 현재 상태 유지 |

AI 담당자의 기존 답변서에서 제안한 incident_id·event_id·stage·analysis_status 구조를 참고했다. 이 규격은 백엔드에서 먼저 시험 가능하게 만든 제안이며 실제 AI 코드와의 최종 합의·연결을 완료한 것은 아니다.
실제 카메라를 켜거나 영상을 분석하는 기능을 만든 것이 아니다. AI 또는 게이트웨이가 보내는 결과를 서버에서 연결·저장·반영하는 기능이다.

## 버튼으로 확인하기

1. 기존 서버 창에서 Ctrl+C를 누른 뒤 safehome-backend 폴더의 start-admin-demo.cmd를 실행한다. 또는 `.\.venv\Scripts\python.exe run.py`를 입력한다.
2. http://127.0.0.1:8000/admin-test 에서 Ctrl+Shift+R로 새로고침한다.
3. 위쪽 ‘시연 대상’을 선택하고 ‘카메라 재검증’ 영역의 ‘① 의심 시작’을 누른다. 주의 상태와 사건 ID가 나온다.
4. ‘② 낙상 확정’을 누른다. 같은 사건 ID가 유지되며 해당 사고가 위험으로 바뀐다. ‘같은 요청 재전송’을 눌러 중복 처리 안내가 나오는지도 본다.
5. ‘① 의심 시작’으로 새 사건을 만든 뒤 ‘② 오탐 취소’를 누른다. 해당 사건이 취소 기록으로 바뀐다. 이전 확정 사건을 취소하는 버튼은 아니다.
6. 다시 새 사건을 시작하고 ‘카메라 실패’ 또는 ‘카메라 시간 초과’를 누른다. 정상으로 바뀌지 않고 의심 상태를 유지한다. 이후 ‘낙상 확정’으로 재시도할 수 있다.
7. ‘이 사건 상세 보기’에서 현재 재검증 상태와 초기·최종 이력을 확인한다. ‘재검증 응답 JSON’에서 duplicate와 state_updated도 확인할 수 있다.

이 영역은 시작할 때 선택한 대상과 사건을 계속 처리한다. 도중에 위쪽 대상 선택을 바꾸더라도 기존 사건의 최종 결과가 다른 사람에게 적용되지 않는다. ‘의심 시작’을 다시 누르면 새 사건이 생기며 이전 사건은 삭제되지 않는다.
이벤트가 많이 들어오면 실시간 기록은 최신 50개만 표시한다. 개별 사건 상세의 재검증 이력도 최근 50개를 반환하고 더 있으면 assessment_history_has_more=true로 알린다. 원본 이벤트 기록은 DB에 남는다.

## 연동용 제안 API

POST /api/v1/ingest/fall-assessments

게이트웨이 인증 토큰이 필요하다. 현재 개발용 gateway-demo-token은 기존처럼 첫 가상 대상의 게이트웨이와 직속 장치 범위만 처리한다. 보호자·어르신 앱이 이 장치 수신 API로 판단 결과를 작성하지 않는다.
관리자 확인용으로 POST /api/v1/mock/fall-assessments도 제공한다. 같은 입력·같은 처리 규칙을 사용하며 관리자만 호출할 수 있다.

| 공통 필드 | 의미 |
|---|---|
| incident_id | 송신 측에서 한 번 만든 사건 UUID. 초기·최종·실패·재시도에 같은 값 사용 |
| event_id | 개별 전송 UUID. 같은 요청의 재전송은 동일 ID·본문 유지 |
| senior_id, device_id | 대상과 보고 장치 UUID. 초기 사건과 같은 대상·게이트웨이여야 함 |
| occurred_at | 시간대가 포함된 ISO 8601 시각. 서버는 UTC로 정규화 |
| stage | PRELIMINARY 또는 FINAL |
| analysis_status | 아래 표의 분석 상태 |
| confirmed_fall | 완료된 최종 확정/오탐 취소일 때만 true/false. 그 외 null 또는 생략 |
| camera_confidence | 선택 0~1. 의미가 확인된 카메라 신뢰도만 제공, 불가 상태에는 보내지 않음 |
| summary | 1~300자 설명 |

| 단계 | analysis_status | confirmed_fall·confidence |
|---|---|---|
| PRELIMINARY | PENDING_VERIFICATION | 둘 다 null 또는 생략 |
| FINAL | COMPLETED | confirmed_fall은 boolean 필수. 신뢰도는 선택 |
| FINAL | CAMERA_UNAVAILABLE / CAMERA_TIMEOUT / INSUFFICIENT_DATA | 둘 다 null 또는 생략 |

1차 의심 예시:

```json
{
  "incident_id": "11111111-1111-4111-8111-111111111111",
  "event_id": "22222222-2222-4222-8222-222222222222",
  "senior_id": "00000000-0000-4000-8000-000000000101",
  "device_id": "dc7ae1e3-6c16-55d0-9141-6c6ba993ede2",
  "occurred_at": "2026-11-18T01:00:00Z",
  "stage": "PRELIMINARY",
  "analysis_status": "PENDING_VERIFICATION",
  "summary": "센서 낙상 의심"
}
```

최종 결과는 같은 incident_id에 새로운 event_id를 사용하고 stage=FINAL, analysis_status=COMPLETED, confirmed_fall=true 또는 false를 보낸다. 카메라 검증 불가는 FINAL·CAMERA_UNAVAILABLE·confirmed_fall=null이다.
device_id와 시각은 설명용이다. 실제 연결에는 조회한 장치 ID와 실제 이벤트 시각을 사용한다.

confirmed_fall=false는 이 제안 API에서 ‘최종 오탐 취소’ 요청을 뜻한다. 원시 카메라 camera_confirmed=false나 AI의 UNKNOWN을 검토 없이 이 값으로 치환하지 않는다. AI의 MEDIUM 등 융합 결과가 남는 경우까지 이 취소 규칙을 그대로 적용해도 되는지는 공동 협의가 필요하다.
신뢰도·ToF 확률·융합 점수는 서로 같은 값으로 간주하지 않는다. 현재 새 단계별 입력은 센서 수치를 임의로 채우지 않으며, 카메라 신뢰도는 기존 evidence.ai_fall_confidence와 별도의 assessment.camera_confidence에 보관한다. 영상·스냅샷 업로드는 이번 범위에 없다.

## 처리 순서와 중복 규칙

최종 입력 전에 초기 의심이 있어야 한다. FINAL이 먼저 도착하면 PRELIMINARY_REQUIRED(409)를 반환하며 그 입력을 저장하거나 정상으로 처리하지 않는다. 송신 측은 초기 입력 확인 후 동일 최종 요청을 재전송할 수 있다.
동일 event_id·동일 본문은 duplicate=true이며 부작용을 반복하지 않는다. 같은 event_id·다른 본문은 EVENT_ID_CONFLICT(409)다.
같은 incident_id에 새 event_id로 PRELIMINARY를 또 보내면 INCIDENT_ID_CONFLICT(409)다. 기존 일회성 /ingest/risk-events로 만든 사고도 새 재검증 사고로 덮어쓰지 않는다.
최종 결과가 COMPLETED가 된 후 다른 판정으로 뒤집는 요청은 ASSESSMENT_ALREADY_FINAL(409)다. 다른 전송 ID로 같은 완료 결과를 다시 보내면 별도 수신 이력에 applied=false를 남기고 사고·현재 상태·알림은 반복하지 않는다. 판정·신뢰도·설명이 모두 같아야 한다.
같은 사건의 마지막 반영 시각보다 오래된 결과는 OUT_OF_ORDER_ASSESSMENT(409)다. 서로 다른 사건이 겹치면 더 새로운 사건을 근거로 한 현재 상태는 과거 사건 결과가 덮어쓰지 않는다. 과거 사건 자체의 최종 기록은 갱신할 수 있다.
카메라 실패·시간 초과 이후에는 새 event_id로 최종 검증을 재시도할 수 있다. 이 서버는 카메라를 직접 호출하거나 정해진 초를 기다렸다 자동으로 시간 초과를 만들지는 않는다. CAMERA_TIMEOUT을 누가 언제 전송할지는 AI·게이트웨이와 정해야 한다.

## 조회·실시간·모의 알림

기존 사고 목록과 상세 URL은 유지한다. 사건의 incident_id·초기 event_id·사건 발생 시각은 초기 기록을 유지하고, 위험 단계·설명·상태를 갱신한다.
최종 오탐 취소 시 사고 기록의 risk_level은 초기 CAUTION을 보존하고 status=CANCELLED로 표시한다. 현재 대상의 상태는 이 사건이 현재 상태의 근거일 때 NORMAL로 바뀐다. 카메라 취소는 취소 제스처와 다르므로 gesture_cancelled를 true로 바꾸지 않는다.
사고 상세에 assessment, assessment_history, assessment_history_has_more를 추가한다. 예전 일회성 사고는 assessment=null, 이력=[]다. 초기·실패·최종 결과의 원본은 ingested_events에 남으며 적용 여부는 새 연결 테이블에서 관리한다.
상태가 바뀌면 기존 STATUS_CHANGED, 사고가 갱신되면 INCIDENT_ALERT를 보낸다. 새로운 이벤트 종류를 추가하지 않았다. INCIDENT_ALERT의 stage·analysis_status·confirmed_fall을 보고 최종 확정·취소·판단 보류를 구분하고 사고 상세를 다시 조회한다.
기존 보호자·관리자 실시간 경로를 재사용하며 어르신 본인 채널에 사고 경고를 추가하지 않는다.
초기 CAUTION은 실시간 의심 기록만 생성한다. 최종 낙상 확정은 FALL_ALERT 모의 알림 기록을 한 번 생성한다. 이전 사건의 늦은 확정도 해당 사건의 확정 알림 기록은 남지만 더 최신 현재 상태를 바꾸지는 않는다. 알림 시점·문구와 늦은 결과의 표시 정책은 실제 연결 전에 협의한다. 실제 FCM/Expo 발송은 아직 하지 않는다.

## DB 변경과 남은 작업

incident_assessment_events 연결 테이블 1개·4개 열을 추가했다: assessment_seq, event_id, incident_id, applied. 기존 원본과 사고 기록에 외래키로 연결한다. 전체는 21개 테이블·141개 열, DB 버전 4다.
기존 DB에 테이블과 인덱스를 추가하는 방식이며 기존 표를 지우거나 갈아엎지 않는다. 이전 버전의 가상 데이터 초기화도 새 연결 기록을 올바른 순서로 지우도록 갱신했다. 초기화 버튼을 누르면 기존처럼 시연 자료는 초기화되므로 이번 기능 확인을 위해 초기화를 할 필요는 없다.
WBS의 ‘카메라 재검증 결과 반영·중복 이벤트 제어’는 서버 모의 구현·검증 단계까지 진행한 것으로 기록한다. 실제 카메라·AI와 연결한 완료 상태가 아니다.
추가로 할 일은 실제 AI 출력→이 API로의 변환 합의, 초기/최종 사건 ID 생성·전송 주체, 센서 시각 동기화·재시도 규칙, 카메라 시간 초과 기준과 실제 영상 시험이다. MQTT 수신과 실제 FCM 전송은 별도 미구현 작업으로 남아 있다.


## 검증 결과와 증빙

전체 자동 시험 **87개 통과**, 실패 0개. 기존 64개와 재검증 관련 23개를 포함한다. TestClient 사용 중단 예정 경고 1건은 동일하다.
동일 사건 연결·확정·취소·실패 후 재시도·일반 요청 재전송·새 전송 ID의 중복 결과·다른 판정으로 덮어쓰기 거부·순서 역전·다른 대상 및 같은 대상의 다른 게이트웨이 차단을 검증했다.
이전 사건의 늦은 확정·취소가 새로운 사건의 현재 상태를 덮어쓰지 않는지, 최근 이력 50개 제한, 재시작 후 유지·초기화 외래키 순서·기존 v3 DB의 모든 행 보존 후 v4 확장도 확인했다.
실제 브라우저의 별도 메모리 DB에서 1차 의심→카메라 실패→낙상 확정까지 사건 ID가 유지되는 것을 확인했다. 같은 요청 재전송 후 사고 수와 이력 수가 늘지 않음을 확인했다. 새 의심 사건의 오탐 취소·정상 상태·상세 재검증 결과도 확인했다.
새 JS 모듈에 브라우저가 이전 파일을 섞어 로드하는 문제가 있어 모듈 경로에 같은 버전 번호를 붙였고, 다시 로드한 화면에서 동작을 확인했다.
현재 코드와 OpenAPI 일치. HTTP 34개 경로·일반 요청/응답 예시 36개 중 요청 본문 13개·응답 32개 모델 검증 통과. 별도 카메라 예시 4단계와 상세 이력도 검증했다. 새 JavaScript 문법 검사 통과.
실제 사용자 DB를 시연 데이터로 바꾸거나 초기화하지 않았다. 기존 로컬 DB의 읽기 전용 스냅샷 백업을 data/before-camera-workflow-20261118.sqlite3에 보관했다. 이 파일은 개인 DB와 동일하게 외부 전달 자료에 포함하지 않았다.
증빙 화면: outputs/카메라재검증_확정과중복확인_2026-11-18.jpg
신규 타입·OpenAPI·예시·DB 사전·SQL·ERD 모델을 갱신했다. 2026-11-22에는 /design/의 그림도 21개 테이블·141개 열·33개 관계로 갱신했다. 이전 18개 표 그림은 이력 폴더에 보관한다.

## 노션에 기록할 진행 상태

‘카메라 재검증 결과 반영·중복 이벤트 제어’는 **진행 중 — 백엔드 모의 구현·검증 완료, 실제 AI·카메라 연동 예정**으로 기록한다.
현재 구현은 사건 연결과 서버의 결과 반영이다. 실제 카메라 모델 구현·AI 규격 최종 합의·현장 성능 검증까지 완료한 것으로 표시하지 않는다. MQTT 수신과 실제 FCM 전송은 별도 후속 작업이다.
